# ADR-0011. Датасет из сцен и дообучение головы детекции: манифест, сплиты по сценам, ONNX

- **Статус:** принято
- **Дата:** 2026-11-23
- **Этап:** 10 (Датасет и дообучение)
- **Связанные требования:** T10-01…T10-08, G10-01…G10-06

## Контекст

Этап 10 замыкает цикл «сцена → датасет → обучение → метрики → ONNX».
Голова детекции должна дообучаться на синтетике без GUI и без ручной
разметки, а результат — проверяться метрикой и выгружаться в формат,
который читает борт. Нужно решить шесть вопросов:

1. Откуда брать разметку, чтобы она не расходилась с кадром?
2. Как доказать, что датасет воспроизводим, а не «примерно такой же»?
3. Как разделить train и val, чтобы метрика не была завышена утечкой?
4. Какую голову обучать, чтобы обучение укладывалось в минуты на CPU?
5. Где хранить метрики обучения и оценки, чтобы отчёт читал их из БД?
6. В каком формате отдавать веса борту и чем проверять экспорт?

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Отдельная аннотация кадров | Привычный формат | Расхождение с кадром не исключено |
| Рамки по маске того же рендера | Согласованность по построению | Разметка только для того, что рендерится |
| Ручная разметка части кадров | Ближе к реальности | Дорого, невоспроизводимо в CI |
| Манифест с sha256 каждого файла | Воспроизводимость проверяется сравнением | Манифест растёт с числом кадров |
| Хэш только конфигурации | Компактно | Не ловит изменение рендера или кода |
| Сплит по кадрам | Больше кадров в val | Кадры одной сцены в обоих сплитах |
| Сплит по сценам | Утечки нет по построению | Меньше валидационных кадров |
| Большая готовая сеть (YOLO-класс) | Высокое качество сразу | Тяжёлые зависимости, минуты на эпоху |
| Своя маленькая голова CenterNet-типа | Секунды на эпоху, полный контроль | Ниже потолок качества |
| Метрики в stdout | Просто | Отчёт и БД расходятся |
| Метрики в `run.sqlite` этапа 9 | Один источник, фильтры и артефакты | Зависимость от схемы журнала |
| ONNX с динамическими осями | Универсально | Бортовая конвертация требует статики |
| ONNX с фиксированными формами | Готов к RKNN/NBG | Один размер входа на модель |
| Сверка через onnxruntime | Привычно | Ещё одна зависимость |
| Сверка через OpenVINO | Уже в зависимостях | Проверяет граф, а не только числа |

## Решение

1. **Разметка снимается с того же рендера, что и кадр.** `SyntheticSceneSource`
   строит раскладку из seed сцены, рендерит кадр и маску, а рамка объекта —
   это охватывающий прямоугольник пикселей его маски. Ключевые точки —
   восемь углов габарита, спроецированные камерой. Объекты, перекрытые
   или обрезанные больше порога `min_visibility`, в разметку не попадают:
   рамка «видимой части» не совпала бы с целым объектом по IoU (T10-01).
2. **Воспроизводимость — сравнением хэша манифеста.** Манифест хранит
   конфигурацию, план сплитов, счётчики и запись на каждый файл (кадр,
   разметка, маска) с sha256. `manifest_hash` считается по содержимому
   без полей происхождения (`manifest_hash`, `created_at`, `run_id`): две
   сборки с одним seed дают один хэш, с разным — разные, и хэш не зависит
   от часов. Это и есть проверяемое свойство G10-01 (T10-01).
3. **Сплиты строятся по сценам, а не по кадрам.** `plan_splits` перемешивает
   сцены seed'ом и отдаёт непересекающиеся `train`/`val`; `SplitPlan`
   отвергает пересечение в конструкторе, а тест проверяет, что каждая сцена
   встречается ровно в одном сплите. Поэтому метрика val не может быть
   завышена кадрами обучающих сцен (T10-02, G10-02).
4. **Аугментация — воспроизводимые деградации бортового канала.** Шум,
   экспозиция, размытие, отражение, потеря кадра и рассинхронизация метки
   выводятся из `(seed, номер кадра)`, а не из глобального генератора.
   Поэтому один и тот же кадр с одним seed аугментируется одинаково, и это
   проверяется сравнением пикселей и параметров (T10-03). В обучении
   аугментация по умолчанию выключена: на синтетическом домене она снижает
   mAP (0,55 против 0,63), поэтому остаётся возможностью датасета, а не
   обязательным шагом тренера.
5. **Голова — своя маленькая сеть с выходом в сетке.** Вход 96×72, шаг 4,
   выходы: тепловая карта классов, логарифмы размеров и смещения центра.
   Логарифм размера даёт одинаковую относительную ошибку для мелкого
   и крупного объекта. Тренер — Adam с косинусным расписанием, чекпойнт
   каждую эпоху, отмена через `threading.Event` сохраняет прогресс,
   `resume` продолжает с номера эпохи (T10-04).
6. **Метрики пишутся в журнал этапа 9.** Обучение и оценка — такие же
   прогоны, как симуляция и конвейер: `kind="training"`/`"evaluation"`,
   метрики `train.*` и `eval.*`, чекпойнт и манифест — артефакты. Отчёт
   читает `eval.map50` из БД, поэтому цифра в отчёте и в журнале одна
   и та же. `RUN_KINDS` расширен, `runs list --kind` знает новые виды
   (T10-05, G10-04).
7. **ONNX экспортируется с фиксированными формами, а сверяется эталонной
   реализацией ONNX.** Вход `image: [1, 3, 72, 96]`, выходы `heatmap/size/
   offset`, opset 17. Динамические оси не используются: бортовая конвертация
   в RKNN/NBG требует статических форм. Критерий гейта — `ReferenceEvaluator`
   из пакета `onnx`: он считает ровно тот граф, что записан в файл, на NumPy,
   и поэтому одинаков на всех платформах (расхождение 1·10⁻⁶, допуск 1e-4).
   Прогон через OpenVINO идёт следом и пишется в отчёт отдельным числом:
   на разных CPU он выбирает разные свёрточные ядра, и его расхождение
   с PyTorch может быть на четыре порядка больше (на AVX-512 раннере
   1,2·10⁻² против 1·10⁻⁶) при том же графе. Поэтому OpenVINO — проверка
   рантайма, а не гейта (T10-06, G10-05).
8. **CLI повторяет пакеты без Qt.** `dataset build|info`, `train`, `eval`,
   `export-onnx` вызывают те же функции, что тесты и будущая вкладка;
   полный цикл выполняется без окна и пишется в журнал (T10-07, G10-06).

## Следствия

- Плюс: датасет воспроизводим побайтово по seed; манифест — единственный
  источник истины о содержимом, а `dataset info` не требует пересборки.
- Плюс: утечки сплитов нет по построению, а не по договорённости; это
  проверяется тестом на реальном манифесте.
- Плюс: полный цикл на 4 сценах × 80 кадров — сборка 3,4 с, обучение
  120 эпох ~136 с на двух потоках CPU; гейт mAP@0.5 = 0,642 при пороге 0,60.
- Плюс: метрики и артефакты лежат в том же журнале, что прогоны симуляции
  и конвейера: `runs show <id> --prefix eval.` и экспорт в Parquet работают
  без нового кода.
- Минус: разметка существует только для того, что умеет рендерить сцена;
  перенос на реальные кадры потребует источника-адаптера.
- Минус: потолок качества ограничен маленькой головой; mAP 0,64 — предел
  домена, а не запаса архитектуры.
- Минус: манифест растёт линейно с числом кадров (sha256 на файл); для
  больших наборов понадобится сжатие или разбиение на страницы.
- Минус: аугментация выключена в тренере по умолчанию — это осознанное
  решение по измерению, а не забытая опция.
- Минус: `onnx` добавлен в runtime-зависимости ради легаси-экспортёра;
  новый экспортёр потребовал бы `onnxscript` и динамических осей.
- Минус: сверка через OpenVINO не годится как критерий: её расхождение
  зависит от ядер CPU. Поэтому вердикт даёт эталонная реализация ONNX,
  а число OpenVINO остаётся справочным.
- Проверки в гейте: G10-01 (хэш манифеста), G10-02 (нет утечки сцен),
  G10-03 (mAP@0.5 ≥ 0,60), G10-04 (метрики в БД), G10-05 (ONNX 1e-4),
  G10-06 (цикл без GUI).
