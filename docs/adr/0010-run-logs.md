# ADR-0010. Журнал прогонов: SQLite рядом с проектом, батчевая запись и экспорт рядов

- **Статус:** принято
- **Дата:** 2026-11-22
- **Этап:** 9 (Логи и метрики)
- **Связанные требования:** FR-LOG-01…FR-LOG-15, T9-01…T9-07, G9-01…G9-06

## Контекст

Этап 9 сохраняет след прогона: симуляция этапа 7 и конвейер этапа 8
дают отчёты с событиями, метриками план/факт, артефактами и разметкой.
След нужен трём потребителям: вкладке «Журналы», CLI `simorph runs`
и будущему датасету этапа 10. Нужно решить пять вопросов:

1. Где хранить журнал, чтобы он не раздувал переносимый `project.json`
   и не менял эталонный хэш документа?
2. Как записать 10^5 рядов без потери и без 10^5 коммитов?
3. Как читать выборки из 10^5 строк, не замораживая интерфейс?
4. Как экспортировать ряды так, чтобы pandas не терял типы меток времени?
5. Что делать с прогоном, который остался в статусе `running` после kill?

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Журнал внутри `project.json` | Один файл | Документ растёт, хэш нестабилен, правка кода меняет проект |
| Отдельный SQLite рядом с проектом | Схема и хэш не меняются, журнал архивируется отдельно | Второй файл рабочего места |
| JSON-lines на прогон | Просто, потоково | Нет фильтров и индексов, выборка требует полного чтения |
| Parquet на прогон | Колоночное чтение | Нет транзакций и частичной записи, сложно дописывать |
| SQLite без WAL | Один файл | Читатель блокирует писателя, kill оставляет горячий журнал |
| SQLite с WAL и `synchronous=NORMAL` | Читатели не блокируют, восстановление автоматическое | Рядом появляются `-wal`/`-shm` |
| Один коммит на строку | Простая логика | 10^5 коммитов, минуты вместо секунды |
| Батч на транзакцию | Быстро, частичная запись откатывается целиком | Теряется максимум текущий батч |
| Метрики в отдельных таблицах по именам | Быстрый точечный фильтр | Схема растёт с каждым новым именем |
| Одна таблица `metrics` с индексом `(run_id, name, t_ns)` | Схема стабильна, фильтры по индексу | Имена составные, нужен префиксный поиск |
| Экспорт CSV только | Без новых зависимостей | Строки и числа теряют типы при чтении |
| CSV и Parquet через pyarrow | Типы сохраняются, pandas читает напрямую | Одна зависимость и её версия в lock |

## Решение

1. **Журнал — отдельный файл `run.sqlite` рядом с проектом.** Схема
   и хэш `project.json` не меняются, поэтому миграции и эталонный файл
   этапа 1 остаются нетронутыми. Путь по умолчанию даёт
   `default_log_path()`, явный путь принимают CLI и вкладка (T9-01).
2. **Схема из шести таблиц.** `runs` — прогон (вид, статус, seed,
   `project_hash`, объект, версия), `run_events` — события с `t_ns`
   и `payload_json`, `metrics` — ряды `(name, value, unit, t_ns, tags_json)`,
   `artifacts` — файлы с хэшем и размером, `annotations` — разметка кадров,
   `settings` — версия схемы. Внешние ключи каскадные, индексы покрывают
   прогон, имя метрики, время, тип события, статус и дату старта.
   Создание идемпотентно: `CREATE TABLE IF NOT EXISTS` плюс запись версии.
3. **WAL и батчевая запись.** `journal_mode=WAL` и `synchronous=NORMAL`
   дают чтение во время записи и автоматический откат незавершённой
   транзакции. Ряды пишутся порциями по 5000 внутри транзакции на порцию:
   10^5 строк записываются меньше секунды, а kill теряет максимум текущую
   порцию, не ломая базу (T9-02, T9-05).
4. **Чтение — словари с параметризованными фильтрами.** `RunStore.metrics`
   фильтрует по точному имени или префиксу, интервалу и прогону; имена
   и интервалы не склеиваются в SQL-строку. Выборка из 10^5 по индексу
   укладывается в единицы миллисекунд, поэтому вкладка читает её
   в фоновом потоке, а синхронные методы остаются для тестов (T9-03).
5. **Незавершённый прогон становится `interrupted`.** При открытии журнала
   `recover_incomplete()` переводит `running` в `interrupted` с причиной
   «процесс прерван». Это явное состояние в списке, а не тихое исправление;
   завершённые прогоны и закоммиченные батчи не трогаются (T9-05).
6. **Экспорт — CSV и Parquet с фиксированными типами.** Колонки заданы
   таблицей `EXPORT_COLUMNS`; Parquet пишется через pyarrow с `int64`
   для `id`, `t_ns` и `seed` и `float64` для `value`. CSV остаётся
   текстовым, JSON-поля — строками, чтобы не терять вложенность. Запись
   идёт через временный файл: недописанная выгрузка не выглядит готовой
   (T9-04).
7. **CLI и вкладка используют один пакет.** `simorph runs list|show|export|
   annotate|prune` работает без Qt; `--log` у `sim run` и `pipeline run`
   пишет прогон тем же `record_to_file`. Вкладка «Журналы» (F11) показывает
   те же ряды и выгружает ту же выборку, поэтому CLI и GUI не расходятся
   в трактовке фильтров (T9-06).

## Следствия

- Плюс: журнал можно удалить, архивировать или очистить `runs prune`,
  не затрагивая проект; переносимый `project.json` остаётся компактным.
- Плюс: 10^5 рядов пишутся за 0,7 с, выборка по имени и интервалу —
  за 4 мс; интерфейс не замирает на больших журналах.
- Плюс: kill процесса не требует ручного ремонта: `integrity_check` даёт
  `ok`, незавершённый прогон виден как `interrupted`.
- Плюс: Parquet читается pandas с `int64`/`float64`, метки времени
  не превращаются в строки.
- Минус: рядом с проектом появляются `run.sqlite` и служебные `-wal`/`-shm`;
  их нужно учитывать при резервном копировании.
- Минус: батчевая запись теряет незакоммиченную порцию при kill — это
  осознанный компромисс ради скорости; потеря ограничена размером батча.
- Минус: pyarrow добавлен в runtime-зависимости, lock-файл фиксирует
  версию; CSV-экспорт остаётся доступным без Parquet.
- Минус: имена метрик составные (`node.<id>.p95_ms`), поэтому фильтр
  по точному имени и префиксу — разные режимы; вкладка различает их
  по точке на конце.
- Минус: отдельный экспорт журнала в JSON-lines (FR-LOG-14) в гейт G9
  не входит; ряды доступны через CSV/Parquet, а `runs show --json` отдаёт
  прогон целиком.
- Проверки в гейте: G9-01 (четыре таблицы), G9-02 (10^5 без потерь),
  G9-03 (фильтры и неблокирующий интерфейс), G9-04 (типы Parquet),
  G9-05 (kill), G9-06 (CLI без GUI).
