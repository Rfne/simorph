# ADR-0007. Модель миссии: граф элементов, бюджет по критическому пути и обмен

- **Статус:** принято
- **Дата:** 2026-11-21
- **Этап:** 6 (Упражнения и миссии)
- **Связанные требования:** FR-MSN-01…FR-MSN-15, T6-01…T6-08, G6-01…G6-06

## Контекст

Этап 6 добавляет конструктор поведения: упражнение содержит миссии, миссия —
граф элементов с таймингами и зависимостями, а редактор показывает граф,
выбранный элемент и параметры одновременно. Нужно решить четыре вопроса:

1. Чем считать миссию: списком шагов или графом?
2. Как допускать повтор участка, не превращая миссию в произвольный граф
   с недоказуемой завершаемостью?
3. Как считать время миссии, где ветви идут одновременно?
4. Что делать с внешним пакетом командного контура, который приходит
   из «Проработки» и не является файлом проекта?

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Линейный список шагов | Просто считать и рисовать | Нет ветвлений и повторных участков, `parallel` не выразить |
| Произвольный граф с циклами | Максимальная выразительность | Завершаемость недоказуема, валидатор не может отличить замысел от ошибки |
| DAG + `loop` с лимитом итераций | Повтор выразим и ограничен, порядок и слои считаются | Повтор только целым участком, а не произвольным переходом |
| Сумма длительностей как бюджет | Одна строка кода | Ветви `parallel` считаются дважды, бюджет завышен |
| Критический путь (ASAP) | Совпадает с исполнением, даёт расписание и ширину параллелизма | Нужен обход графа, а не сумма |
| Пакет командного контура как проект | Всё в одной схеме | Внешний артефакт перезаписывается, `coordination` превращается в исполняемый алгоритм |

## Решение

1. **Миссия — ориентированный граф.** Узел — `MissionElement` из 12 типов
   MVP (TRD 5.7), ребро — `next`. Реестр `ELEMENT_SPECS`
   (`core/mission/elements.py`) хранит категорию для панели графа,
   обязательные поля и терминальность; редактор, валидатор и отчёт читают
   один и тот же контракт.
2. **Цикл допускается только через `loop`.** Обратное ребро из элемента
   типа `loop` — легальный повтор с явным `iterations`; обратное ребро
   из любого другого элемента — ошибка графа. Так миссия остаётся
   обозримой, а завершаемость ограничена лимитом итераций.
3. **Граф никогда не бросает исключений.** Битые ссылки, дубликаты,
   циклы и недостижимые узлы — данные для валидатора и подсветки в
   редакторе. Панель графа показывает проблему сразу, не дожидаясь
   проверки.
4. **Слои — по самому дальнему предшественнику.** Раскладка панели графа
   строится релаксацией ограничения «слой потомка больше слоя родителя»;
   ветви `parallel` расходятся в стороны и не накладываются.
5. **Бюджет — критический путь.** Раннее расписание (ASAP) даёт каждому
   элементу момент старта и окончания; бюджет — максимум окончаний, сумма
   длительностей считается отдельно как «сколько было бы без параллелизма».
   Ширина параллелизма — пик одновременно выполняемых элементов. Самый
   жёсткий `ttl_s` миссии сравнивается с бюджетом.
6. **Пять классов замечаний.** Ссылки (`next`, `zone`, `sensor`), граф
   (один `start`, цикл только через `loop`, достижимость), обязательные
   входы и ветви `parallel`, тайминги (TTL против длительности, предел
   часа, бюджет против TTL), geofence и высота (поза внутри участка и зоны,
   0…120 м) плюс совместимость сенсора: `observe` и `capture` требуют
   камеру. Пути замечаний совпадают с путями pydantic, поэтому панель
   валидации открывает нужное поле.
7. **Обмен — та же схема раздела.** JSON и YAML содержат ровно
   `Mission`/`ExerciseSection` (`model_dump(mode="json")`), формат
   выбирается по расширению. Импорт **read-only**: миссия из файла или
   пакет командного контура (`tasks`, `route`, `constraints`,
   `coordination`, `degradation`) читается в память и не пишется обратно;
   задачи не из MVP попадают в предупреждения, `coordination` остаётся
   контекстом, а не исполняемым алгоритмом.
8. **Редактор — три панели одного документа.** Граф, элемент и параметры
   пересобираются из одного расчёта (`build_graph`, `mission_budget`,
   `mission_issues`), поэтому расходятся только при ошибке в коде, а не
   при правке. Правка идёт через `DocumentStore.set_value` — одной
   командой undo. Компактный режим скрывает панель графа, сохраняя выбор.

## Следствия

- Плюс: CLI, редактор и тесты используют один расчёт — «в окне одно,
  в файле другое» не бывает.
- Плюс: `loop` с лимитом итераций делает повтор выразимым и проверяемым;
  цикл без `loop` отклоняется до запуска.
- Плюс: бюджет по критическому пути совпадает с исполнением на этапе 7,
  где супервизор пойдёт по тому же расписанию.
- Минус: повтор только целым участком, произвольный переход назад
  не выразить — это осознанное ограничение MVP.
- Минус: ASAP не учитывает ресурсы и занятость агента; приоритеты
  (`priority`) хранятся, но в расписании пока не участвуют.
- Минус: пакет командного контура отображается частично: задачи не из
  MVP видны только как предупреждения, `coordination` не исполняется.
- Минус: `loop` не разворачивается в бюджет: итерации не умножают
  длительность участка, бюджет считается по одному проходу.
- Проверки в гейте: G6-01 (упражнение с двумя миссиями), G6-02 (пять
  классов ошибок), G6-03 (синхронность трёх панелей и компактный режим),
  G6-04 (бюджет и отклонение отрицательных таймингов), G6-05 (read-only
  импорт), G6-06 (воспроизводимость экспорта и импорта).
