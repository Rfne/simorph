# ADR-0002. Проект как один JSON-документ из семи разделов

- **Статус:** принято
- **Дата:** 2026-11-20
- **Этап:** 1 (Ядро проекта)
- **Связанные требования:** FR-UX-01, NFR-REL-03, NFR-REP-03, TRD 5.1, 5.11, 8.1

## Контекст

Проект объединяет профиль заказчика, мир, агентов, упражнения, конвейеры и
отчёты. Их можно было бы хранить набором файлов (`profile.json`, `world.json`,
…), как перечислено в TRD 8.1. Но тогда появляются проблемы: частичный набор
файлов, рассинхронизация версий разделов, невозможность атомарно сохранить
согласованное состояние и посчитать единый хэш конфигурации.

## Решение

1. Проект — **один** файл `project.json`, содержащий семь разделов:
   `project`, `profile`, `world`, `agent`, `exercise`, `pipeline`, `report`.
   Отдельные `*.json` из TRD 8.1 остаются форматом экспорта и импорта, но не
   основным хранилищем.
2. Каждый раздел несёт собственное поле `schema_version`: разделы развиваются
   независимо, и миграция одного не должна переписывать остальные.
3. Неизвестные поля **запрещены** (`extra="forbid"`). Опечатка в имени поля
   даёт ошибку с путём, а не молчаливое игнорирование данных.
4. Запись только атомарная: временный файл → `fsync` → `.bak` → замена.
   Сбой на любом шаге оставляет исходник целым (NFR-REL-03).
5. Хэш конфигурации — sha256 по каноническому JSON: сортировка ключей,
   разделители без пробелов, время в UTC с точностью до секунды. Хэш не
   зависит от порядка ключей, форматирования файла и часового пояса машины.
6. Переводы строк в файле всегда `\n`, кодировка UTF-8 без BOM: иначе
   golden-тесты расходятся между Windows и Linux.
7. Блокировка — файл `project.json.lock` с pid, хостом и пользователем.
   Блокировка от завершившегося процесса считается устаревшей и снимается
   только по явному подтверждению (`takeover_stale`).

## Последствия

- Плюс: одно сохранение — одно согласованное состояние; единый хэш для
  манифеста прогона и воспроизводимости (NFR-REP-03).
- Плюс: валидатор собирает все замечания сразу и указывает путь к полю,
  поэтому UI может перейти к ошибке.
- Минус: файл растёт вместе с проектом. Для MVP (единицы агентов и миссий)
  это приемлемо; при росте — вынести крупные разделы в отдельные файлы со
  ссылками по хэшу, не меняя внешнего контракта.
- Минус: запрет лишних полей требует миграции при добавлении любого поля.
  Поэтому любое расширение схемы сопровождается шагом миграции и записью
  в `CHANGELOG`.

## Альтернативы

| Вариант | Почему отклонён |
|---|---|
| Набор отдельных файлов на раздел | Нет атомарности и единого хэша, возможны неполные наборы |
| YAML вместо JSON | Медленнее, неоднозначности с типами и якорями, лишняя зависимость |
| SQLite как хранилище проекта | Проект должен быть переносимым текстовым файлом и читаться глазами |
| Разрешить лишние поля | Опечатки и «мусор» из старых версий проходят молча |
